### Протокол сессии

Каждая рабочая сессия идёт по одному сценарию:

1. Прочитать «Текущую позицию» и «Открытые вопросы». При выборе и планировании подэтапа сверяться с видением ([docs/VISION.md](docs/VISION.md)).
2. Взять первый незакрытый подэтап из списка «Порядок работ» (раздел 4). Через пункты списка не перескакивать (исключения — задачи «(опц.)» и исправление дефектов). Замечания из ежедневного использования (FEEDBACK.md) идут раньше списка.
3. Перед нетривиальным подэтапом — короткий план реализации на 3–7 пунктов и явные допущения.
4. Реализовать → тесты → проверка Definition of Done.
5. Обновить PLAN.md: чекбоксы, статус этапа, «Порядок работ», «Текущая позиция», при необходимости — «Открытые вопросы» и «Журнал изменений плана».
6. Краткий отчёт: что сделано, что дальше, что требует решения пользователя.

### Definition of Done подэтапа

1. Код компилируется без предупреждений (`TreatWarningsAsErrors`), `dotnet format --verify-no-changes` проходит.
2. Для нового кода написаны тесты (модульные и/или интеграционные); `dotnet test` зелёный целиком.
3. Для UI-работ пройден ручной сценарий из `docs/QA_CHECKLIST.md`.
4. Документация обновлена: README (если менялось поведение продукта), ARCHITECTURE/ADR (если менялись решения), USER_GUIDE (если менялся пользовательский сценарий).
5. PLAN.md обновлён.
6. Изменения закоммичены в формате Conventional Commits; один подэтап = 1–3 коммита.

### Правила изменения плана

- Решение из раздела 2 можно пересмотреть только с записью в «Журнал изменений плана» и новым ADR.
- Новые задачи добавляются в соответствующий подэтап; новая крупная функция — в этап 12 или отдельным этапом и в список «Порядок работ».
- Приоритет — сначала удобство, затем красота, затем оптимизация (видение, ADR-0010). Бюджеты раздела 8 — сигнал регресса, а не запрет: функция из видения из-за бюджета не откладывается. Если она выводит метрику за бюджет, сразу после неё в порядок работ ставится подэтап оптимизации, обязательный до ближайшего релиза. Регресс, заметный пользователю (задержка ввода, подвисание окна), — дефект удобства и исправляется сразу.

- [x] `ExclusionMatcher` — собственный glob с кэшем (`GlobPattern`: точное имя, `*.ext`, `prefix*` без регулярных выражений, остальное — скомпилированный `Regex`; шаблон с разделителем сравнивается с путём от корня), стандартный набор (`$RECYCLE.BIN`, `System Volume Information`, `node_modules`, `.git`, `bin`, `obj`, `*.tmp`, а также `~$*`, `*.crdownload`, `*.part`), скрытые и системные по параметрам корня, размер, глубина; `IsPathExcluded` для событий наблюдателя
- [x] Прогресс `IndexProgressEvent { RootId, Phase (Enumerating / Writing / Sweeping / Done), Scanned, Written, CurrentPath, RatePerSecond, Elapsed }` не чаще 4 раз в секунду, смена фазы — всегда (`ProgressReporter`)
- [x] Отмена и пауза (`PauseTokenSource`/`PauseToken`, проверка перед каждой папкой); потоки сканера выделенные, `ThreadPriority.BelowNormal` и `THREAD_MODE_BACKGROUND_BEGIN` (`ThreadBackgroundPriority`)
- [x] Ошибки доступа записываются в `scan_log` (`IScanLogRepository`) и не прерывают обход; записи непрочитанных папок сохраняются (`MarkSubtreeAsync`)

#### 2.2 Конвейер записи

- [x] Producer/consumer через ограниченный `Channel<EntryBatch>` (ёмкость 4 пакета, противодавление); пакеты по 5 тыс. (настройка `BatchSize`); единственный писатель `SqliteWriter` (`ScanPipeline`)
- [x] Полное сканирование как mark-and-sweep: `NextScanIdAsync`, пометка, `SweepAsync`/`SweepSubtreeAsync`; при недоступном корне индекс не трогается, исчезнувшее или исключённое поддерево удаляется
- [x] Пропуск неизменённых строк (тип, имя, размер, время изменения, атрибуты совпадают) — строка только помечается. Метаданные папок берутся из самой папки, а не из данных перечисления: NTFS обновляет копию в записи родителя лениво, и без этого каждое сканирование «меняло» недавно тронутые папки
- [x] События `EntriesChanged` агрегируются по папкам (`FolderChangeSet`, до 256 папок, дальше — «изменился весь корень»)

#### 2.3 Слежение (`FileSystemWatcher`)

- [x] `FileSystemRootWatcher` на каждый корень: `IncludeSubdirectories`, `NotifyFilters = FileName | DirectoryName | LastWrite | Size | Attributes`, `InternalBufferSize = 64 КБ`
- [x] Склейка (`ChangeCoalescer`): пакет готов после паузы 400 мс (настройка), но не позже 900 мс от первого события; повторы сводятся к одной проверке пути; переименования сохраняются по порядку (цепочки); временные файлы (`~$`, `.tmp`, `.crdownload`, `.part`) — через стандартные исключения
- [x] Применение (`ChangeApplier`): переименование — перенос поддерева одним запросом с сохранением идентификаторов, остальное — проверка пути на диске: есть — создание или обновление, нет — удаление поддерева; запись появляется, только если родитель в индексе (скрытые и исключённые папки не просачиваются); новая папка — сверка её поддерева (перенос в корень извне)
- [x] Переполнение буфера (`InternalBufferOverflowException`) и сбой применения → сверка корня с обычным приоритетом; во время полного сканирования наблюдатель помечает записи его номером и перепроверяет тронутые пути после него (`RootIndexState`)
- [x] Исчезновение диска или сети → корень Offline, наблюдатель останавливается, индекс сохраняется; опрос доступности раз в 30 с и перезапуск со сверкой; сбой наблюдателя при живом корне — перезапуск наблюдателя со сверкой
- [x] UNC-корни: плановая сверка вчетверо чаще. Предупреждение о ненадёжности событий в интерфейсе — этап 9 (настройки корней)

#### 2.4 Оркестрация (`IndexerService`)

- [x] При старте: корни из репозитория → наблюдатели → полное сканирование (первый раз или после восстановления индекса, `IndexerOptions.ForceFullScan`) или сверка. Обёртка hosted service — вместе с сервером на этапе 4
- [x] Сверка (`ReconcileRunner`) — по разнице, а не по mtime папок: обход папок, сравнение содержимого каждой с её детьми в индексе, запись только отличий (добавления, изменения, удаления, смена регистра с сохранением идентификатора). Mtime папки не меняется при правке файла, поэтому сверка только по нему пропускала бы изменённые файлы; чтение стоит столько же, а записей почти нет. Плановая сверка каждые 6 ч (настройка `ReconcileIntervalMinutes`); привязка к ночи или простою — этап 10
- [x] Очередь (`IndexTaskBacklog`) с приоритетами: сверка поддерева по событию наблюдателя > сверка корня > полное сканирование; поглощение покрытых задач; одна задача на физический диск (`disk:N` по `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`) и на корень, до двух дисков одновременно
- [x] Управление: `PauseAll`, `ResumeAll`, `RescanRoot`, `ReconcileRoot`, `RebuildAllAsync`, `RefreshRootsAsync`; `GetStatuses` на корень и `GetAggregateState` для иконки трея (Idle / Indexing / Paused / PartiallyOffline / Error)
- [ ] (опц.) Пауза тяжёлых задач при работе от батареи (`GetSystemPowerStatus`) — отложено до этапа 10

#### 2.5 Метаданные

- [x] Вид файла по расширению (`FileKindMap`); признак облачной заглушки `FileEntry.IsCloudPlaceholder` по атрибутам `RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN` и `OFFLINE` — содержимое таких файлов не читается (сканер и наблюдатель его не читают вовсе)
- [ ] (опц.) Лёгкие метаданные (размеры изображений, длительность медиа) в отдельной низкоприоритетной очереди — отложено до этапа 12 (предпросмотр)

#### 2.6 Тесты и бенчмарки

- [x] Генератор тестовых деревьев `TestTree` (`tests/DiskApp.Testing`): N файлов, глубина, junction и junction-цикл, папка без доступа (`icacls`), путь длиннее 260 символов, Unicode-имена
- [x] Тесты сканера: полнота, порядок «родитель раньше детей», исключения, скрытые, глубина, цикл не зацикливает, недоступное не валит, длинные и Unicode-пути, поддерево, отмена и пауза
- [x] Тесты наблюдателя на реальной файловой системе (с ожиданием): create / modify / delete / rename файла и папки; 1 000 быстрых изменений → индекс согласован (при переполнении — через сверку); одно изменение — меньше 1 с; переполнение, сбой и пауза
- [x] Проверка бюджетов `dotnet run -c Release --project tests/DiskApp.Benchmarks -- scan-budget`: 100 тыс. файлов — 4,5 с (≤ 60 с), пик рабочего набора +79 МБ (≤ 100 МБ), сверка без изменений 0,9 с, повторное полное сканирование 0,85 с; дескрипторы и память не растут от прогона к прогону

### Этап 3 — Поиск

**Статус:** ✅ (2026-10-11) · **Объём:** L · **Версия:** v0.3 · **Зависит от:** 1, 2

**Цель.** Быстрый и предсказуемый поиск с фильтрами и ранжированием, пригодный для поиска по мере ввода.

#### 3.1 Парсер запроса

- [x] Токенизатор: слова, фразы в кавычках, фильтры `ключ:значение`, отрицание `-`, диапазоны (`size:>10mb`, `size:1mb..5mb`, `modified:2026-01..2026-03`), (опц.) `/regex/` — `QueryParser`, регулярное выражение проверяется на корректность и применяется к кандидатам
- [x] Фильтры: `ext`, `type`, `in`, `root`, `size`, `modified`, `created`, `is`, `tag`, `fav`; синонимы и значения на RU и EN (`type:картинки`, `modified:неделя`) — `FilterValues`
- [x] Устойчивость: незакрытые кавычки, неизвестные фильтры трактуются как текст; позиции токенов для подсветки и подсказок
- [x] Тесты: таблица из ≥ 60 случаев; round-trip через `ToString()` — 89 случаев в `QueryParserTests`

#### 3.2 Исполнение запроса

- [x] Стратегия по длине терма: ≥ 3 символа — FTS5 trigram `MATCH`; 1–2 символа — префикс по индексу `name COLLATE NOCASE` с лимитом; пустой запрос — подборка (недавние, избранные) — префикс идёт по `name_folded` (ADR-0005: `NOCASE` не сворачивает кириллицу), короткие и отрицательные термы проверяются `instr` по `name_folded`, `LIKE` не используется
- [x] Фильтры → параметризованный `WHERE`: `in:` по `root_id` и префиксу `rel_path`; `type:` по `kind`; даты через UTC-границы — `in:` по имени папки разворачивается в непересекающиеся диапазоны `rel_path` во временной таблице (`CROSS JOIN` и проверка функцией с двоичным поиском); границы дат считаются в часовом поясе пользователя
- [x] Пагинация keyset по `(score, id)`; лимит кандидатов (например 2 000) до ранжирования — курсор `SearchCursor`, лимит 2 000; при усечении к выборке добавляются записи с именем на первый терм, недавние и избранные
- [x] Отмена долгих запросов (прерывание через `sqlite3_interrupt` по `CancellationToken`), таймаут 500 мс с частичным результатом и флагом
- [x] Экранирование спецсимволов FTS (`"`, `*`, `-`), тесты генерации SQL и защиты от инъекций — термы уходят в `MATCH` фразой в кавычках, весь SQL на параметрах

#### 3.3 Ранжирование

- [x] Компоненты score: тип совпадения (точное имя > начало имени > начало слова > подстрока > нечёткое), доля покрытия имени, bm25 из FTS, frecency = Σ log(1 + opens) · decay(дни с последнего открытия), избранное, штраф за глубину пути, свежесть изменения — без bm25 (ADR-0005: дорого на частых триграммах и бессмысленно для коротких имён); история весит тем меньше, чем слабее совпадение
- [x] Веса в настройках с пресетами «По имени», «Недавнее», «Сбалансированно» — `RankingWeights`, настройка `RankingPreset`, пресет можно передать в запросе
- [x] Детерминированный tie-break по имени и пути
- [x] Golden-тесты на фиксированном корпусе (~500 записей): ожидаемый топ-5 для ~30 запросов — `SearchGoldenTests`

#### 3.4 Нечёткое совпадение и подсветка

- [x] Fuzzy-скорер в духе fzf: последовательные символы, бонусы за границы слов, camelCase и разделители, штраф за разрывы — над кандидатами из 3.2 — `FuzzyMatcher`: подпоследовательность с выравниванием как в fzf v2 плюс приблизительная подстрока (расстояние Дамерау — Левенштейна) для опечаток; кандидаты по любой из триграмм, порог похожести 0,8, включается при < 5 точных совпадениях
- [x] Диапазоны подсветки для имени и пути; Unicode: кириллица, ё/е, нормализация NFKD для диакритики (опц.) — ё/е сворачиваются (`SearchText.Fold`); опциональная NFKD не сделана

#### 3.5 Поисковый сервис

- [x] `SearchService.SearchAsync(request, ct)` → `SearchPage { Hits, ApproxTotal, ElapsedMs, ParsedQuery, Warnings }` — `TotalCount` с флагом `IsTotalApproximate`, `Elapsed`, `IsPartial`, `IncludesFuzzy`, `NextCursor`

- [x] `SuggestAsync`: история, популярные фильтры, автодополнение значений (`ext:` из индекса, `tag:` из тегов, `in:` из папок)

#### 3.6 Производительность

- [x] Генератор синтетической БД на 1 млн записей с фиксированным seed — `search-budget` в `tests/DiskApp.Benchmarks` (seed 42, словарь RU/EN, дерево папок по годам, история открытий и избранное)

### Этап 16 — Модуль резервного копирования

**Статус:** ⬜ · **Объём:** 16.1 — M, 16.2 — XL · **Версия:** 16.1 — v1.0 (выполняется после этапа 10, до релиза в этапе 11), 16.2 — v1.x · **Зависит от:** 16.1 — этапы 1, 4, 9; 16.2 — этапы 2, 4, 8 и 16.1

**Цель.** Пользователь не теряет ни данные DiskApp (настройки, корни, избранное, теги, коллекции, статистику, индекс), ни, по своему решению, сами файлы. Модуль настраиваемый: что копировать, куда, как часто, сколько хранить, как проверять и как восстанавливать.

**Что защищаем**

| Данные | Ценность | Восстановление |
|---|---|---|
| `settings.json` | Высокая | Из копии |
| Метаданные в `index.db`: корни, избранное, теги, коллекции, история запросов, статистика использования | Высокая, невоспроизводимы | Из копии БД или из JSON-экспорта метаданных |
| Индекс файлов в `index.db` | Средняя, воспроизводим пересканированием | Из копии (быстро) или пересканирование (долго на больших дисках) |
| Кэш иконок и миниатюр | Нулевая | Не копируется, пересоздаётся |
| Файлы пользователя в корнях | По решению пользователя | Задания резервного копирования (16.2) |

#### 16.1 Резервное копирование данных приложения (v1.0)

- [ ] `IBackupService` в Core, реализация в Infrastructure; снимок БД через SQLite Online Backup API (`SqliteConnection.BackupDatabase`) — консистентная копия во время работы, индексация и поиск не останавливаются, файлы `-wal` и `-shm` не трогаются
- [ ] Состав копии: снимок `index.db`, `settings.json`, `manifest.json` (версия приложения, версия схемы БД, дата, размеры, SHA-256 каждого файла, состав); упаковка в `DiskApp-backup-YYYYMMDD-HHmmss.zip`; вариант «только метаданные» — JSON-экспорт корней, избранного, тегов, коллекций, истории и статистики без индекса (маленький файл, переносим между версиями и машинами)
- [ ] Расписание: вручную; при выходе из приложения; ежедневно или еженедельно в заданное время при простое; автоматически перед миграцией схемы, пересборкой индекса, восстановлением и обновлением приложения — «страховочная» копия
- [ ] Назначения: по умолчанию `%LocalAppData%\DiskApp\backups`; любая папка пользователя, в том числе синхронизируемая облачным клиентом (OneDrive, Google Drive) или сетевая (UNC); несколько назначений одновременно; недоступное назначение — предупреждение и повтор позже
- [ ] Хранение: оставить N последних; схема «дни / недели / месяцы» (GFS); лимит общего размера; автоматическое удаление старых; страховочные копии хранятся отдельно (последние 3)
- [ ] Шифрование по желанию: AES-256 с паролем пользователя (пароль не хранится, ключ выводится через PBKDF2 или Argon2); настоятельно предлагается, когда в настройках появляются токены удалённого доступа (этап 13)
- [ ] Восстановление: список копий с датой, размером, версией и статусом проверки; проверка `PRAGMA integrity_check` и контрольных сумм до замены; выбор «всё / только настройки / только метаданные / только индекс»; текущие данные перед заменой уходят в страховочную копию; аккуратный перезапуск приложения
- [ ] Автовосстановление: при повреждённой БД на старте (1.3) предложить последнюю проверенную копию вместо пересборки с нуля
- [ ] Экспорт и импорт метаданных в JSON как самостоятельные действия: перенос на другую машину, слияние избранного и тегов с существующими, разрешение конфликтов
- [ ] Совместимость версий: копия хранит версию схемы; восстановление старой копии в новую версию проходит через миграции; новая копия в старую версию — отказ с понятным сообщением
- [ ] API и события: `GET /backups`, `POST /backups` (создать сейчас, с параметрами состава и назначения), `GET /backups/{id}`, `POST /backups/{id}/verify`, `POST /backups/{id}/restore`, `DELETE /backups/{id}`, `GET /backups/settings`, `PUT /backups/settings`, `POST /metadata/export`, `POST /metadata/import`; SignalR `OnBackupProgress`, `OnBackupCompleted`
- [ ] Интерфейс: «Настройки → Данные → Резервные копии» (расписание, назначения, хранение, шифрование, «Создать сейчас», «Восстановить…», журнал копий); `InfoBar` при сбое копирования; напоминание, если копия давно не делалась (настраивается) — сбой и напоминание идут через модуль уведомлений (этап 21)
- [ ] Тесты: снимок во время активной записи в БД консистентен; ретенция удаляет ровно лишнее; восстановление возвращает настройки и метаданные один в один; шифрование и расшифровка; повреждённый архив отклоняется; импорт метаданных со слиянием

**Критерии готовности 16.1**

- Копия создаётся по расписанию без заметного влияния на поиск и индексацию (замер).
- Восстановление из любой копии возвращает настройки и метаданные один в один (автотест).
- Страховочная копия делается перед каждой миграцией, пересборкой и восстановлением.

#### 16.2 Резервное копирование файлов пользователя (v1.x)

- [ ] Модель «задание»: источник (корень, папка, коллекция, тег или сохранённый запрос), назначение (папка, внешний диск по идентификатору тома, сетевой путь), режим, расписание, фильтры (исключения, расширения, размер), политика удалений, число хранимых версий, способ проверки
- [ ] Режимы: зеркало (односторонняя синхронизация; удалённые в источнике файлы помечаются и удаляются из назначения через N дней), версионный (изменённые файлы сохраняются с меткой времени, хранится K версий), снимок (zip-архив на дату)
- [ ] Инкрементальность через индекс: изменения из этапа 2 (watcher, mtime, размер) дают список «что изменилось с последнего запуска» без повторного обхода; опциональная проверка xxHash64 для подозрительных файлов (размер тот же, mtime новее)
- [ ] Расписание и триггеры: вручную; по расписанию; «при подключении диска» (`DriveInfo` и `WM_DEVICECHANGE`); «непрерывно» с задержкой тишины (например 10 минут после последнего изменения); пауза на батарее и на лимитном подключении
- [ ] Выполнение через `FileOperationService` (4.5): очередь, прогресс, отмена, ограничение скорости, низкий приоритет ввода-вывода; журнал запусков (скопировано, пропущено, ошибки); отчёт по завершении; повтор неудавшихся файлов
- [ ] Восстановление: просмотр содержимого назначения, восстановление файла или папки в исходное либо указанное место, список версий файла в версионном режиме, сравнение источника и копии
- [ ] Облачные назначения — только через папки клиентов синхронизации; прямые API облаков — отдельное решение позже (вопрос 12)
- [ ] API: `GET /backup-jobs`, `POST /backup-jobs`, `PUT /backup-jobs/{id}`, `DELETE /backup-jobs/{id}`, `POST /backup-jobs/{id}/run`, `POST /backup-jobs/{id}/cancel`, `GET /backup-jobs/{id}/runs`, `GET /backup-jobs/{id}/runs/{runId}`, `POST /backup-jobs/{id}/restore`; события `OnBackupJobProgress`, `OnBackupJobCompleted`
- [ ] Интерфейс: страница «Резервное копирование» в `NavigationView` (список заданий, состояние, последний и следующий запуск), мастер создания задания, страница запуска с журналом, панель восстановления; действие «Добавить в задание…» в контекстном меню файла и папки
- [ ] Тесты: все режимы на временных папках; политика удалений; версии; инкрементальный запуск после изменений; отключение диска посреди запуска; восстановление байт-в-байт по хэшам

**Критерии готовности 16.2**

- Задание на 100 тыс. файлов без изменений выполняется инкрементально за секунды.
- Восстановление возвращает файлы байт-в-байт (автотест с хэшами).
- Сбой диска посреди запуска не оставляет назначение в неконсистентном состоянии: журнал фиксирует, повтор доделывает.

### Этап 17 — Разбор входящих: папки-накопители и быстрая сортировка

**Статус:** 🔄 (2026-10-11: этап был пропущен при переходе 8 → 9 и по запросу пользователя сделан раньше 16.1 и 11; сделаны срез 17.0 — страница «Разбор», — 17.2 — карточка рабочей папки — и 17.1 — очередь накопителей (2026-10-12); остальное пересмотрено по видению и идёт по порядку работ раздела 4: 17.5 → 17.4) · **Объём:** L · **Версия:** v0.6 (17.0), v0.7 (17.2), v0.8 (17.1, 17.5, 17.4) · **Зависит от:** 2 (слежение), 3 (поиск папок), 4.5 (операции), 8.4–8.5 (операции в интерфейсе), 19 (авто-теги — для 17.5) · **Решения:** 18, 19, 23, ADR-0012

**Сценарий.** Файлы приходят отовсюду — Skype, почта, браузер, мессенджеры — и падают в **папки-накопители**: «Загрузки», «Мои полученные файлы» Skype, любая папка под присмотром. DiskApp помогает разложить их по **рабочим папкам** (TCI2, 417, Soft): в подпапку, с новым именем и тегами. Файлы, имя которых совпадает с шаблоном рабочей папки, раскладываются сами. «Общий склад → профильные склады» — исходная аналогия пользователя; в интерфейсе и документах — «папка-накопитель» и «рабочая папка».

**Принципы.** Разбор — короткая работа на одной странице: выбрал файлы → рабочая папка (клавиши 1–9) → «Перенести». При разборе приложение только перемещает и никогда не удаляет само. Каждое решение отменяется. Всё, что сделал авторазбор, видно в истории файлов (этап 20).

**Пересмотр 2026-10-11** (видение, ADR-0012). Отменены:

- профильные склады с профилями, доменами, статистикой и каскадом;
- отдельное окно разбора `TriageWindow` с однобуквенными клавишами;
- общий механизм правил.

Рабочая папка получает номер, авто-теги (этап 19) и шаблоны имён (17.5). Напоминание о разборе переехало в общий модуль (этап 21), журнал решений — в историю файлов (этап 20), быстрый перенос с настройкой — в область 2 окна Drag&Drop (18.3).

### Этап 19 — Авто-теги рабочих папок

**Статус:** 🔄 (2026-10-12: 19.1–19.4 сделаны; поиск `tag:` только по авто-тегу вне бюджета — 19.5 по ADR-0010, по просьбе пользователя — после 17.1 и 17.5) · **Объём:** M · **Версия:** v0.7 · **Зависит от:** 3 (поиск, фильтр `in:`), 8.7 (теги), 17.2 (карточка рабочей папки) · **Решения:** 22, ADR-0012

**Цель.** Тег, заданный рабочей папке, действует на все файлы внутри неё и её подпапок — текущие и новые — и помогает искать без ручной расстановки (видение, пункт 2).

#### 19.1 Модель и хранение

- [x] Авто-теги хранятся один раз у папки и переживают переименование папки (в том числе через Проводник), пересканирование и пересборку индекса. Входят в экспорт метаданных и в резервную копию (16.1) — 2026-10-12: миграция V002, таблица `folder_tags (path, tag_id)` — полный путь папки, а не запись индекса: пересборка удаляет записи (и с ними `entry_tags`), а строки папок остаются; `SqliteFolderTagRepository`. Путь следует за переименованием тем же `SortingFolderTracker`, что и пути папок разбора (событие наблюдателя и переносы через очередь операций), со сбросом кэша поиска. Таблица лежит в той же базе — в резервную копию 16.1 попадёт без отдельной работы; отдельного экспорта метаданных в DiskApp пока нет
- [x] Авто-теги задаются рабочей папке и любой её подпапке. Теги файла — его явные теги плюс авто-теги всех папок выше — 2026-10-12: авто-теги можно задать любой папке внутри корней (`PUT /api/v1/auto-tags`); сама папка тоже получает свои авто-теги. В ответах API у записи — `inheritedTags` с папкой-источником (ближайшая первой, без повторов своих тегов)
- [x] Явные теги работают как раньше и переезжают вместе с файлом; авто-тег файл теряет, когда уходит из папки — 2026-10-12: принадлежность считается по пути на лету, поэтому вынесенный файл теряет авто-тег сразу, а новый получает его без записи в базу
- [x] Удаление рабочей папки из списка (карточка или меню чипа) спрашивает, снять ли её авто-теги; файлы не трогаются (перенесено из 17.2) — 2026-10-12: «Снять» / «Оставить»; оставленные авто-теги продолжают действовать. Снять авто-теги можно и у пропавшей папки (сервер не требует, чтобы она существовала, если список пуст)

#### 19.2 Поиск

- [x] `tag:x` находит файлы с явным тегом `x` и всё внутри папок с авто-тегом `x` — диапазонами `rel_path`, как фильтр `in:`. Отрицание `-tag:x` и подсказки `tag:` учитывают авто-теги — 2026-10-12: папки с авто-тегом переводятся в корень и относительный путь; сама папка — точным совпадением (диапазон «417…» захватил бы соседнюю «417 ТЗ»), потомки — диапазоном, авто-тег корня — весь корень. Запрос только из фильтров берёт кандидатов объединением «свои теги ∪ папки ∪ диапазоны потомков» по индексу путей, а не обходом таблицы. Подсказки `tag:` идут из той же библиотеки тегов — авто-теги в ней уже есть
- [x] Чипы тегов в строках быстрого поиска, «Поиска», «Обзора», «Разбора» и в карточке файла показывают и унаследованные теги — 2026-10-12: общий шаблон `TagChipTemplate`: свой тег — на подложке, авто-тег — контуром с подсказкой «Авто-тег папки …»
- [x] Замер `tag:` с авто-тегами на 1 млн записей. Выход за бюджет поиска — подэтап оптимизации следом (ADR-0010) — 2026-10-12: `search-budget` дополнен 40 рабочими папками с авто-тегом и областью на 5 % записей. Остальные запросы в бюджете (p95 2–50 мс), `tag:тз report` — 45 мс, `-tag:проект report` — 27 мс; запросы только из `tag:` — вне бюджета: `tag:тз` 64 мс, `tag:проект ext:pdf` 124 мс (до объединения по индексу путей было 134 и 331 мс). Подэтап 19.5 поставлен в порядок работ следом

#### 19.3 Интерфейс

- [x] Поле «Авто-теги» в карточке рабочей папки (17.2) с подсказками из библиотеки тегов; в «Обзоре» — действие «Авто-теги папки…» в меню папки — 2026-10-12: `AutoTagsEditorViewModel` и `AutoTagsEditorView` — чипы с крестиком, поле с `Enter`, подсказки, строка «Уже получает от папок выше: …»; новые имена становятся тегами с цветом из палитры. - [ ] Поиск находит файлы и по прежним именам и путям: ниже результатов — секция «Было»: «перемещён в …», «переименован в …», «в корзине с 12.10». Фильтр для таких записей — имя при реализации

#### 20.6 API и тесты

- [ ] `INotificationService`: вид, заголовок, текст, действия, важность; общие лимиты частоты, «не беспокоить» и часы тишины

- [ ] (опц.) Список последних уведомлений в приложении

- [ ] «Напомнить…» в меню файла и папки (быстрый поиск, «Поиск», «Обзор», «Разбор») и без файла — с текстом. Срок: через час, вечером, завтра, дата и время. Режим: точно или в удобный момент

## 6. Сквозные практики

### Git и коммиты

- `main` всегда собирается и проходит тесты; работа в ветках `feat/<этап>-<кратко>`, `fix/…`, `chore/…`, `docs/…`.
- Conventional Commits с областью: `feat(index): …`, `fix(search): …`, `perf(ui): …`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.
- Один подэтап — 1–3 коммита (или один PR). Теги релизов `vX.Y.Z` по SemVer.

### Тестирование

- Пирамида: модульные тесты Core → интеграционные Infrastructure и Server → headless UI → ручной чеклист.
- Временные папки и БД только через фикстуры с гарантированной очисткой: `TemporaryDirectory` и `TemporaryDatabase` из `tests/DiskApp.Testing`.
- Нестабильный тест уходит в карантин с задачей на исправление, а не удаляется.

## 7. Риски и смягчение

| Риск | Влияние | Смягчение |
|---|---|---|
| `FileSystemWatcher` теряет события (переполнение буфера, сеть, сон) | Расхождение индекса с диском | Debounce и обработка переполнения пересканированием; периодическая сверка; mark-and-sweep при полном сканировании |
| Облачные файлы «по запросу» (OneDrive) скачиваются при чтении | Трафик, место, медленная индексация | Проверка атрибутов `RECALL_ON_DATA_ACCESS` / `OFFLINE`; не читать содержимое и миниатюры таких файлов |
| Размер базы на целых дисках (2+ млн файлов) | Сотни МБ, медленные вставки | FTS только по имени (S4: 161 МБ на 1 млн записей против 334 МБ с путями); даты целыми тиками; замер 3.6 — 389 МБ на 1 млн записей реальной схемы, из них FTS 75 МБ (ADR-0007); бюджет пересмотрен до 450 МБ (ADR-0010); повторный замер на реальном индексе — 10.6 |
| Mica и Acrylic нестабильны на части конфигураций | Визуальные артефакты | Fallback на сплошной фон; переключатель в настройках; проверка на Windows 10 |
| Антивирусы реагируют на глобальные хуки | Ложные срабатывания, удаление exe | `RegisterHotKey` вместо хуков; подпись кода |
| Порт loopback занят или Kestrel заблокирован политикой | Приложение не стартует | Динамический порт с повтором; понятное сообщение; (опц.) именованные каналы |
| Quick Switch зависит от внутренностей системных диалогов | Ломается после обновлений Windows | Флаг «экспериментально», таймауты, откат, UI Automation как альтернатива |
| Списки Avalonia на 10 тыс.+ элементов | Лаги прокрутки | Виртуализация, лимит результатов, подгрузка страницами |
| Kestrel внутри процесса увеличивает память и время старта | Бюджеты | S3: 138 мс и +17 МБ — укладывается в бюджеты; параллельный старт; ReadyToRun |
| Ранжирование «не угадывает» | Раздражение, недоверие | Frecency, пресеты, golden-тесты, обратная связь из dogfooding |
| Avalonia Browser тяжёлый (10–20 МБ) | Долгая первая загрузка | Brotli, trimming, кэш; сценарий ограничен локальной сетью |
| Android ограничивает доступ к файловой системе | Нельзя индексировать телефон | Телефон — удалённый клиент к ПК; локальная индексация через SAF — позже |
| Нет подписи кода → предупреждение SmartScreen | Отток пользователей | Подпись (платно) или инструкция; публикация в winget |

## 8. Бюджеты производительности

Цели для v1.0 на машине с SSD и 16 ГБ памяти. Фиксируются с датой и конфигурацией после замера на этапе 10. Бюджеты — сигнал регресса, а не запрет функции (ADR-0010, раздел 1 «Правила изменения плана»).

| Метрика | Цель | Как измеряем |
|---|---|---|
| Старт до появления иконки в трее | < 1 с тёплый, < 2 с холодный | Лог меток времени в `Program.Main` и при создании `TrayIcon` |
| Показ окна быстрого поиска по хоткею | < 100 мс | Метка от `WM_HOTKEY` до первого кадра |
| Поиск p95 на 1 млн записей | < 50 мс (сервис), < 60 мс (через API) | BenchmarkDotNet на синтетической БД; нагрузочный smoke |
| Обновление результатов после ввода | ≤ 100 мс | Метка от `TextChanged` до обновления списка |
| Память в простое | < 150 МБ | `dotnet-counters`, Диспетчер задач после 10 минут простоя |
| CPU в простое | ≈ 0 % | Диспетчер задач, 10 минут без изменений на дисках |
| Первичная индексация (SSD) | ≥ 2 000 файлов/с; 100 тыс. файлов ≤ 60 с | Бенчмарк сканера на сгенерированном дереве |
| Отражение изменения файла | ≤ 1 с | Тест watcher'а с меткой времени |
| Размер БД на 1 млн записей | ≤ 450 МБ (пересмотрено 2026-10-11, ADR-0010, вопрос 15; было ≤ 250 МБ по спайку S4). Замер 408 МБ | Спайк S4, `search-budget` этапа 3.6; на реальном индексе — 10.6 |
| История файлов | ≤ 50 МБ при настройках по умолчанию (90 дней) | Рост базы за неделю ежедневного использования (20.3) |
| Отклик на щелчок по значку в трее | Не больше системного интервала двойного щелчка + 100 мс до показа окна Drag&Drop | Метка от `Clicked` до первого кадра (18.1) |
| Размер установщика | ≤ 80 МБ | Артефакт релиза |

## 9. Глоссарий

| Термин | Значение |
|---|---|
| Корень (Root) | Папка или диск, который пользователь добавил в DiskApp для индексации |
| Запись (Entry) | Файл или папка в индексе |
| Индекс | База SQLite с записями, FTS-таблицей и статистикой |
| Сверка (reconcile) | Частичное пересканирование, которое сравнивает индекс с диском без полного обхода |
| Mark-and-sweep | Полное сканирование с пометкой записей текущим `scan_id` и удалением непомеченных |
| Frecency | Оценка, объединяющая частоту и давность использования файла |
| Быстрый поиск | Всплывающее окно по глобальной горячей клавише |
| Входящие (Inbox) | Папка по умолчанию для всего, что добавлено через DiskApp; с этапа 18.2 — основная папка-накопитель |
| Quick Switch | Перенаправление стандартного диалога «Открыть / Сохранить как» в папку, выбранную в DiskApp |
| Спайк | Короткий одноразовый эксперимент для проверки технического риска |
| Dogfooding | Ежедневное использование собственного продукта разработчиком |
| Страховочная копия | Автоматическая резервная копия данных приложения перед миграцией схемы, пересборкой индекса или восстановлением |
| Задание резервного копирования | Настроенная пользователем связка «источник → назначение» с режимом, расписанием и правилами хранения для файлов (этап 16.2) |
| Папка-накопитель (в исходной аналогии — общий склад) | Папка под присмотром DiskApp («Загрузки», «Мои полученные файлы» Skype), куда файлы сбрасываются отовсюду; новые файлы в ней ждут разбора (этап 17) |
| Основная папка-накопитель | Накопитель с отметкой «основная»; в неё падают файлы, брошенные в область 1 окна Drag&Drop (этап 18.2) |
| Рабочая папка (в исходной аналогии — профильный склад) | Папка, куда раскладываются файлы из накопителей: номер 1–9, авто-теги, шаблоны имён (этапы 17, 19; ADR-0012). Профили и каскад складов отменены |
| Авто-тег | Тег рабочей папки или её подпапки, который наследуют все файлы внутри — текущие и новые; уходя из папки, файл его теряет (этап 19) |
| Шаблон имени рабочей папки | Маска имени (`417_*`); подходящие файлы из накопителей раскладываются в эту папку сами или предлагаются первыми (17.5) |
| Окно Drag&Drop | Окно у значка в трее с областями «Бросить в накопитель» и «Разложить по рабочей папке» (этап 18) |
| Разбор | Раскладка файлов из накопителей по рабочим папкам на странице «Разбор»: выбор, папка, подпапка, имя, теги, «Перенести», отмена |
| Подсказка назначения | Предложенная рабочая папка с объяснением, откуда взялось предложение: шаблон, история решений, недавние |
| История файлов | Постоянный журнал того, что и когда случилось с файлом — через DiskApp или в Проводнике — с возвратом на место (этап 20) |
| Умный момент | Момент для напоминания, который планировщик выбирает по детектору занятости и лимитам частоты; «Отложить» без срока означает «напомни в следующий умный момент» (этап 21) |

# ADR-0001: Архитектурный стиль DiskApp

**Статус:** Принято, ожидает проверки спайками S3 и S4 · **Дата:** 2026-10-10 · **Связано с:** PLAN.md решения 1–4 и 13, этапы 0.6, 1, 3, 4, 6

## Контекст

DiskApp — десктопное приложение в трее для быстрой работы с файлами, которое позже должно получить Android- и веб-клиенты. Пользователь задал стек: .NET 10, Avalonia UI, Web API, SignalR, SQLite. Нужно решить, как эти части соединяются внутри одного десктопного процесса, как хранится индекс и как устроен поиск по именам файлов, чтобы уложиться в бюджеты: показ окна < 100 мс, поиск p95 < 50 мс на миллионе записей, память в простое < 150 МБ.

## Решение

1. **Локальный сервер внутри процесса десктопа.** `DiskApp.Server` (ASP.NET Core) запускается внутри `DiskApp.Desktop` на Kestrel, слушает только `127.0.0.1` на динамическом порту. Интерфейс общается с ядром исключительно через `DiskApp.Client` (REST + SignalR) по loopback. Тот же сервер можно запустить без интерфейса (служба Windows, headless) и, при включённом удалённом доступе, открыть для локальной сети.
2. **Minimal API с группами endpoints** вместо контроллеров. Версия в пути `/api/v1`. DTO и интерфейсы хаба — в отдельном проекте `DiskApp.Contracts` с JSON source generation.
3. **SQLite через `Microsoft.Data.Sqlite` + Dapper**, схема и миграции — SQL-скрипты во встроенных ресурсах с таблицей `schema_version`. Режим WAL, один писатель через очередь (`Channel`), пул читателей. EF Core не используется.
4. **Полнотекстовый поиск по именам через FTS5 с токенизатором `trigram`** (external content на таблице `entries`). Термы короче трёх символов ищутся префиксом по индексу `name COLLATE NOCASE`. Состав FTS-таблицы (только имя или имя + путь) определяется спайком S4 по размеру БД и задержке.
5. **Файл решения в формате `.slnx`.**

Слои и зависимости: `UI → Client → Contracts`; `Desktop → UI, Server`; `Server → Core, Infrastructure, Contracts`; `Infrastructure → Core`. `UI` не ссылается на `Core` и `Infrastructure` — это проверяется архитектурным тестом.

## Последствия

Плюсы:

- Один путь кода для всех клиентов: десктоп ежедневно проверяет тот же API, который получат Android и Web.
- Сервер отделяем от интерфейса без переписывания: headless-режим и удалённый доступ — вопрос конфигурации.
- SignalR даёт события в реальном времени (прогресс индексации, изменения файлов, ход операций) всем клиентам одинаково.
- Dapper и прямой SQL дают полный контроль над PRAGMA, пакетными вставками и FTS5; след в памяти минимален.
- Trigram-токенизатор даёт поиск подстрок без учёта регистра за миллисекунды, без собственного индекса в памяти.

Минусы и принимаемые риски:

- Kestrel в процессе добавляет оценочно 200–400 мс к старту и 20–30 МБ памяти; смягчение — параллельный старт с интерфейсом, ReadyToRun; проверяется спайком S3.
- Сериализация на loopback добавляет доли миллисекунды на запрос; для поиска по мере ввода допустимо, проверяется нагрузочным smoke в этапе 4.
- Занятый порт или политика безопасности могут мешать Kestrel; смягчение — динамический порт с повтором, понятное сообщение.
- FTS5 trigram заметно увеличивает размер БД (ориентир ≤ 600 МБ на миллион записей); если спайк S4 покажет больше — FTS только по имени.
- Без EF Core миграции пишутся руками; зато они явные и проверяются тестом апгрейда.
- `.slnx` требует актуальных инструментов (.NET 10 SDK, VS 2026), что в проекте и так выполнено.

## Альтернативы

- **Прямые вызовы ядра из интерфейса (без HTTP).** Быстрее на микросекунды, но два пути кода (десктоп и удалённые клиенты) и API без ежедневной проверки. Отклонено; возможна как оптимизация через второй `IDiskAppApi`, если loopback окажется узким местом.
- **Controllers.** Больше рефлексии и шаблонного кода, хуже дружат с триммингом. Отклонено.
- **EF Core 10.** Удобные миграции и LINQ, но медленнее пакетные вставки, а FTS5 всё равно через raw SQL. Отклонено для хранилища индекса; может вернуться для вспомогательных таблиц, если Dapper станет обузой.
- **`LIKE '%x%'`.** Полное сканирование таблицы, не укладывается в бюджет на миллионе записей. Отклонено.
- **Индекс имён в памяти (как Everything).** Быстро, но десятки мегабайт памяти на миллион записей и собственная реализация поиска. Отложено как возможная оптимизация.
- **`.sln`.** Работает везде, но шумный diff. Отклонено.

## Проверка

- Спайк S3 (этап 0.6): время старта Kestrel в процессе, память, подключение клиента. Порог: старт ≤ 400 мс, память ≤ 30 МБ сверх Avalonia.
- Спайк S4 (этап 0.6): миллион синтетических записей — скорость вставки, размер БД, p95 поиска для 2, 3 и 5 символов. Порог: p95 < 50 мс, размер ≤ 600 МБ.
- Результаты — в ADR-0004 и ADR-0005; при провале порогов решение пересматривается здесь же до начала этапа 1.

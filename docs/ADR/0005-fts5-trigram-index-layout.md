# ADR-0005: FTS5 trigram — состав индекса и короткие запросы

**Статус:** Принято; бюджет размера БД пересмотрен в ADR-0010 (2026-10-11) · **Дата:** 2026-10-10 · **Связано с:** ADR-0001 пункт 4, PLAN.md решение 4, бюджеты раздела 8; этапы 0.6 (спайк S4), 1.2, 3

## Контекст

Поиск подстрок по именам файлов без учёта регистра на миллионе записей должен укладываться в 50 мс (p95), а база — в разумный размер. ADR-0001 выбрал FTS5 с токенизатором `trigram`, но оставил открытым состав таблицы (только имя или имя и путь) и поведение для запросов короче трёх символов, где trigram-индекс не работает.

## Решение

По результатам спайка `spikes/S4.Fts5Trigram` (SQLite 3.53.3 из Microsoft.Data.Sqlite 10.0.12, 1 млн синтетических записей, 30 % кириллицы, external-content FTS, WAL, пакеты по 20 000):

| Состав FTS | Вставка 1 млн | Optimize | Размер файла |
|---|---|---|---|
| Только имя | 7,7 с (129 тыс. строк/с) | 1,6 с | 161 МБ |
| Имя и путь | 16,5 с (60 тыс. строк/с) | 3,1 с | 334 МБ |

| Запрос | Способ | Совпадений | Первые 50 | `COUNT(*)` |
|---|---|---|---|---|
| `rep` (3 символа) | trigram `MATCH` + `ORDER BY rank` | 14 356 | 22 мс | 0,7 мс |
| `rep` | trigram-ускоренный `LIKE '%rep%'` | 14 356 | 0,1 мс | 21 мс |
| `report` (6) | `MATCH` + `rank` | 14 356 | 34 мс | 4,4 мс |
| `202` (3, очень частый) | `MATCH` + `rank` | 306 892 | 532 мс | 14,5 мс |
| `re` (2 символа) | `LIKE` по FTS, полный скан | 123 228 | 0,4 мс | 393 мс |
| `x7` (2, редкий) | `LIKE`, полный скан | 0 | 265 мс | 226 мс |
| `отч` (кириллица) | `MATCH` | 9 287 | 12 мс | 0,6 мс |
| `отч` | `LIKE` | 8 609 | 0,1 мс | 15 мс |
| `invoice 2023` (два слова) | `MATCH` | 646 | 15 мс | 5,7 мс |

1. **FTS только по имени** (решение 4 подтверждено): вдвое меньше база и вдвое быстрее вставка. Путь ищется отдельно — фильтр `in:` по индексированной колонке папки и префиксные запросы, а не через trigram.
2. **Подстрочный поиск начинается с трёх символов** через trigram `MATCH` (несколько слов — все обязательны). Ранжирование — своё (начало слова, frecency, свежесть) поверх кандидатов из `MATCH`, без `bm25`/`rank`: встроенный ранг стоит 20–500 мс на больших выборках и бессмыслен для коротких имён. Для очень частых триграмм набор кандидатов ограничивается (порядка 5 000), чтобы остаться в бюджете 50 мс.
3. **Один–два символа** ищутся префиксом по отдельной колонке `name_folded` (имя в нижнем регистре по правилам .NET) с обычным B-tree индексом плюс недавние и частые файлы. Полный скан на 2 символа стоит 140–390 мс и в бюджет не укладывается; подстрочные совпадения по двум символам малоценны.
4. **Регистр кириллицы.** `LIKE` в SQLite нечувствителен к регистру только для ASCII: `'%отч%'` не находит «Отчёт» (8 609 против 9 287 у `MATCH`). Поэтому `LIKE` по сырому имени не используется: от трёх символов — `MATCH` (trigram сворачивает регистр по Unicode), короче — `name_folded`.
5. **Бюджет размера БД** на 1 млн записей ужесточается с 600 до 250 МБ (161 МБ у индекса по имени плюс колонки реальной схемы). Бюджет первичной индексации (≥ 2 000 файлов/с) ограничивается сканером, а не SQLite: вставка идёт в 60 раз быстрее.

## Последствия

- Схема этапа 1 получает `name_folded` (+~30 МБ на миллион) и индекс по папке для `in:`.
- `COUNT(*)` для больших выборок стоит 5–15 мс — допустимо для строки состояния, но считать стоит после первых 50 результатов.
- Синтетические имена короче реальных путей пользователя; реальный индекс может быть больше — пересчёт на этапе 3.6.
- Размер индекса FTS отдельно от таблицы измерить не удалось: в сборке SQLite нет `dbstat`.

## Альтернативы

- **FTS по имени и пути.** Вдвое дороже по месту и времени, а совпадения по пути нужны редко и закрываются фильтром `in:`.
- **Только `LIKE` без FTS.** 140–400 мс на запрос — вне бюджета.
- **Индекс в памяти.** Сотни МБ на миллион записей против бюджета памяти 150 МБ.
- **Встроенный `rank` (bm25).** Медленно на частых триграммах и не отражает полезность для имён файлов.

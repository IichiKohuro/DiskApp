# ADR-0012: Рабочие папки вместо профильных складов; наследуемые авто-теги; шаблоны имён для авторазбора

**Статус:** Принято · **Дата:** 2026-10-11 · **Связано с:** [VISION.md](../VISION.md) пункты 2, 3 и 7, PLAN.md решения 18, 19, 22 и 23, этапы 17 и 19, ADR-0005, ADR-0011

## Контекст

Исходный замысел этапа 17 (решения 18 и 19) описывал «профильные склады»:

- именованные назначения с профилем: виды файлов, расширения, ключевые слова, домены источника;
- закреплённые номера 1–9 и каскад «склад внутри склада»;
- статистика, мастер создания;
- отдельное окно разбора с десятком однобуквенных клавиш;
- общий механизм правил с условиями.

Срез 17.0 по сценарию пользователя сделал проще: рабочая папка — это путь и подпись в списке `sorting.workFolders`, порядок задаёт клавиши 1–9. Этого хватило для ежедневного разбора.

Видение добавляет две вещи, которых в плане не было:

- **авто-теги** рабочей папки — для всех файлов внутри неё и её подпапок, текущих и новых;
- **авторазбор** файлов, имя которых совпадает с шаблоном рабочей папки.

Пользователь выбрал наследуемые авто-теги. Видение требует не перегружать интерфейс.

## Решение

1. **Рабочая папка — единственная модель назначения при разборе.** У неё есть:
   - путь, подпись и порядок (номер 1–9) — как в 17.0;
   - авто-теги;
   - шаблоны имён для авторазбора;
   - (опц.) шаблон подпапки (`{год}`, `{год}/{месяц}`).

   Профильные склады с профилями, доменами и статистикой, каскад и мастер склада отменены. Таблица `warehouses` из схемы ARCHITECTURE не создаётся. Склад «следующего уровня» заменяют подпапки со своими авто-тегами.
2. **Авто-теги наследуются, а не записываются в каждый файл.**
   - Тег хранится один раз у папки. Он действует на всё внутри неё на любой глубине — на текущие файлы и будущие.
   - Файл, ушедший из папки (в том числе через Проводник), тег теряет. Пришедший — получает.
   - Хранение должно переживать переименование папки, пересканирование и пересборку индекса. Конкретная таблица выбирается при реализации 19.1.
   - Свои авто-теги можно задать и подпапке рабочей папки. Они складываются с тегами родителей.
   - Поиск `tag:x` находит файлы с явным тегом `x` и всё внутри папок с авто-тегом `x`. Для этого служат диапазоны `rel_path` — тот же механизм, что у фильтра `in:` (ARCHITECTURE, раздел 6).
   - Унаследованный тег показывается чипом другого вида с подсказкой «от папки …». Снимается он у папки, а не у файла.
   - Явные теги, поставленные вручную или при разборе, работают как сейчас и переезжают вместе с файлом.
3. **Шаблоны имён — авторазбор.**
   - У рабочей папки задаётся список масок имени (glob: `417_*`, `*TCI2*`; регулярные выражения — опц.). Необязательные условия: накопитель, расширение.
   - Режим шаблона: «переносить автоматически» после «времени успокоения» (этап 17.1) или «только предлагать первым» на странице «Разбор».
   - Файл, подходящий к шаблонам нескольких папок, автоматически не переносится, а предлагается с выбором.
   - Шаблон создаётся из решения одним действием на странице «Разбор»: «Всегда класть такие файлы сюда?» с предпросмотром маски. Есть сухой прогон на текущем содержимом накопителей.
   - Автоперенос идёт обычной операцией очереди. Он пишется в историю файлов (этап 20) и сообщается сводным уведомлением с «Отменить» (этап 21).
4. **Подсказки (решение 18) упрощаются:** шаблоны рабочих папок → история решений по расширению и словам имени → недавние рабочие папки. Профили складов и домены источника из подсказок убраны. Источник из `Zone.Identifier` — опциональный признак.
5. **Отдельного окна разбора `TriageWindow` (17.3) нет.** Разбор идёт на странице «Разбор» и в области 2 окна Drag&Drop (ADR-0011).

## Последствия

- Авто-теги ничего не стоят базе: одна строка на папку, а не на каждый файл. Это важно при бюджете размера базы (ADR-0010).
- `tag:` становится дороже: к выборке по `entry_tags` добавляются диапазоны папок. Замер на 1 млн записей обязателен (этап 19).
- Файл, вынесенный из рабочей папки, «теряет» её теги. Это осознанно: тег принадлежит месту. Если нужно, чтобы тег остался с файлом, его ставят явно.
- Если рабочую папку переименовали или перенесли через Проводник, её путь в настройках должен следовать за ней, иначе папка выпадет из разбора. Это отдельный пункт этапа 19.
- Каскад складов и профили потеряны как идея. Если они понадобятся, вернуться можно новым ADR.

## Альтернативы

- **Записывать авто-тег в каждый файл.** Новые файлы требуют обработки событий наблюдателя. Файлы, вынесенные из папки, уносят устаревшие теги. База растёт на строку на файл и тег, а снятие авто-тега превращается в массовое удаление. Пользователь выбрал наследование.
- **Профильные склады с профилем и каскадом** (исходное решение 19). Дублируют рабочие папки 17.0 и перегружают настройки.
- **Общий механизм правил** (исходный 17.5: условия → действия на отдельной странице). Мощнее, но тяжелее. Шаблоны у рабочей папки покрывают случай из видения. Общие правила можно добавить позже, если шаблонов не хватит.

## Уточнения при реализации этапа 19 (2026-10-12)

- Авто-теги хранятся по полному пути папки (`folder_tags`, миграция V002), а не по записи индекса: пересборка индекса удаляет записи вместе с явными тегами, а авто-теги должны её пережить. Путь меняет та же служба, что и пути рабочих папок (`SortingFolderTracker`).
- Авто-теги задаются любой папке внутри корней, а не только рабочей: в «Обзоре» есть «Авто-теги папки…». Сама папка тоже получает свои авто-теги.
- Сама папка проверяется точным совпадением пути, потомки — диапазоном: диапазон «417…» без разделителя захватил бы соседнюю «417 ТЗ».
- Замер: запросы только из `tag:` на 1 млн записей — 64 и 124 мс при бюджете 50 мс (с текстом — в бюджете). По этому ADR и ADR-0010 следом идёт подэтап оптимизации 19.5.

## Уточнения при реализации этапа 17.5 (2026-10-12)

- Шаблоны хранятся у рабочей папки в настройках (`sorting.workFolders[].rules`), отдельной таблицы нет: шаблонов единицы, и они переезжают вместе с папкой. Условие «только из накопителя» следует за переименованием накопителя.
- Маска без `*` и `?` ищется в любом месте имени: «417» — то же, что `*417*`. Пользователь пишет код проекта, а не glob, и иначе шаблон молча ничего бы не находил.
- Сами переносятся только файлы. Папка из накопителя только предлагается: её содержимое могло ещё дописываться, а «время успокоения» считается по времени изменения самой папки.
- Файл, вернувшийся после автопереноса (отменой или вручную), получает состояние «вручную» и сам больше не уходит — иначе «Отменить» не работало бы. Отменённая пользователем операция авторазбора действует так же.
- Подпапка из шаблона — путь внутри рабочей папки; её нет на диске — файл не переносится, а ждёт ручного разбора (запись в журнале). Шаблон подпапки с `{год}`, `{месяц}` — по-прежнему (опц.).
- Имя при автопереносе — по шаблону имени разбора (`sorting.nameTemplate`), чтобы автоматом и вручную файлы назывались одинаково. Для этого `FileNameTemplate` перенесён в `DiskApp.Contracts.Text`: им пользуются и сервер, и интерфейс.
- Журнал автопереносов — журнал приложения и пометка `origin = AutoSort` у операции; история файлов с отметкой «авторазбор» — этап 20, сводка у трея — этап 21.

## Проверка

- Тесты: унаследованный тег у файла, созданного через наблюдатель; потеря тега при выносе; переименование папки сохраняет теги; авто-теги подпапки складываются с родительскими.
- Бенчмарк `tag:` с авто-тегами на 1 млн записей — в пределах бюджета поиска раздела 8 или задача оптимизации по ADR-0010.
- Тесты шаблонов: совпадение масок, конфликт двух папок, сухой прогон, отмена автопереноса — 2026-10-12: `SortingRuleSetTests`, `AutoSortApiTests` (настоящий сервер), `SortingRulesUiTests`, `SortingMaskTests`.

# ADR-0004: Kestrel внутри процесса десктопа

**Статус:** Принято · **Дата:** 2026-10-10 · **Связано с:** ADR-0001 пункты 1–2, PLAN.md решения 1, 2; этапы 0.6 (спайк S3), 4, 6.2

## Контекст

ADR-0001 выбрал локальный сервер (Minimal API + SignalR на Kestrel) внутри процесса десктопа с общением интерфейса по loopback. Оценка стоимости была умозрительной: 200–400 мс к старту и 20–30 МБ памяти. Нужны измерения, чтобы подтвердить решение и выбрать вариант построения хоста.

## Решение

Решения 1 и 2 подтверждаются. Хост строится через `WebApplication.CreateSlimBuilder` с `AddSignalR()`, адрес `http://127.0.0.1:0`, фактический порт читается из `app.Urls` после `StartAsync`. Контейнер один: сервисы ядра регистрируются в `builder.Services`, интерфейс и оболочка резолвятся из `app.Services` (в спайке singleton из `app.Services` и из хаба — один экземпляр). Сервер стартует в фоне параллельно с Avalonia (этап 6.2), интерфейс ждёт готовности с таймаутом.

## Последствия

Замеры спайка `spikes/S3.KestrelInProcess` (2026-10-10, .NET 10.0.12, Windows 11, 22 CPU, Release):

| Метрика | Значение |
|---|---|
| Старт Kestrel + SignalR, `CreateSlimBuilder`, холодный (с JIT) | 138 мс |
| Прирост рабочего набора после старта | +17 МБ (46,8 МБ у консольного процесса) |
| HTTP GET по loopback: первый / медиана / p95 | 60 мс (JIT) / 0,12 мс / 0,20 мс |
| SignalR: подключение / Invoke медиана / p95 | 68 мс / 0,16 мс / 0,23 мс |
| SignalR push сервер → клиент, медиана | 0,17 мс (200 из 200 доставлено) |
| Рабочий набор после нагрузки | 61 МБ |
| Остановка | 15 мс |
| `CreateBuilder` после прогрева JIT | 50 мс, +2 МБ |

- Стоимость оказалась ниже оценки: при параллельном старте сервер не задерживает появление трея, память укладывается в бюджет 150 МБ.
- Накладные расходы loopback (0,1–0,2 мс на вызов) незначительны относительно бюджета поиска 50 мс; поиск по мере ввода через API допустим.
- Сравнение `CreateSlimBuilder` и `CreateBuilder` в одном процессе некорректно (второй стартовал с прогретым JIT); выбран slim-вариант как достаточный для Minimal API и SignalR и с меньшим следом.
- Риски остаются прежними: занятый порт или политика безопасности — динамический порт с повтором и понятное сообщение.

## Альтернативы

- **Прямые вызовы ядра из интерфейса.** Снова отклонено: выигрыш доли миллисекунды не стоит второго пути кода.
- **Именованные каналы вместо TCP.** Не нужны: loopback быстр и работает для будущих Android и Web.
- **gRPC.** Тяжелее для браузерного клиента, не даёт преимуществ на loopback.

## Проверка

`dotnet run -c Release` в `spikes/S3.KestrelInProcess`, результаты в `results.md`. Повторный замер внутри настоящего приложения — этап 6.2 (сервер в процессе) и 4.7 (нагрузочный smoke).
